# archive —— 已下线的自建 OCR 管线

## 为什么归档

2026-11-16 的决定：**用户上传的文件全量交给官方解析（Files API + document 块），不做自建检索与自建 OCR。**

在这个策略下，自建 OCR 是严格劣于官方解析的：

1. 官方 `rich_layout_recognition` 会把文档里的图表裁出来按原位置喂给模型；我们的 OCR 只拿到归一化坐标，而服务端裁图需要装 poppler 渲染 PDF 页，是新增的原生依赖。
2. 同样 $0.225/1000 页，走 OCR 等于「付 OCR 费 + 再把全文当 token 传给模型」，多付一道还少拿图表。
3. 当初算作优点的「数据不出机器」，在「全文传给模型」的策略下并不成立——文档内容照样会发到 API。

## 这套代码当时做了什么

- 接管 `POST /v1/ocr`，流式转发 multipart 到官方 OCR，网关代持真 Key
- 解析响应：成对提取 `<ref>类型</ref><box>[[x1,y1,x2,y2]]</box>` 元素（坐标归一化 0-1000）
- 清洗正文（剥离 ref 类型标签，否则每段前面都会多一个 `title`）
- 限额校验（1000 页 / 100 MiB）、并发控制、本地落盘、路径穿越防护、旧记录容错
- 24 项单测

## 如果以后重新需要

典型场景：想要本地全文搜索/审计，或想脱离官方 Files API 的 25 GiB / 1 万文件配额。
届时把 `archive/src/*.ts` 挪回 `src/`，恢复 `src/index.ts` 里的路由即可。

⚠️ 已知实测结论（省得重新踩）：
- 坐标**只在** `purpose=rich_layout_recognition` 时返回；`text_recognition` 是纯文本、无坐标
- 官方 token 用的是**全角竖线** `<｜box｜>`，只写半角正则会永远解析不到
- 识别开始后 HTTP 就已是 200，失败信息藏在 body 的 `error` 字段里，不能只看状态码
